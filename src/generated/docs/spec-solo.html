Agent Knowledge Host — Single-Operator Fork (SOLO v1)

Lineage. This is a deliberate fork of the multi-tenant platform spec (agent-knowledge-host-spec-PLATFORM-v2.md), descoped to a single operator with a public read surface. The platform spec is preserved unchanged as the blueprint for "if this ever becomes a service." This document is almost a strict subset: nearly every mechanism here is carried over identically or simplified, so growing back toward the platform is mostly additive, not a rewrite. The one deliberate divergence (not a simplification) is the slug lifecycle — SOLO makes slugs non-reusable where the platform frees them on delete; it is called out in §0 below and, on the platform side, at its freed-slug section, so the lineage stays auditable. Where a platform section was dropped, it is likewise listed in §0 with the reason.

0. What this is, and what was dropped

The itch this actually serves. My agents write reports and other HTML content I want to share externally with nothing more than a link, without the manual copy-into-Google-Drive-then-share dance. This is a personal tool with a public read surface — not a platform.

Three actors, and only three:

  • The operator (me) — the sole owner. Full control: manage agents and keys, write, delete, revoke.
  • Agents — authenticated by per-agent API key; can read and write. Per-agent keys exist specifically so a rogue or compromised agent can be contained (revoked) without disturbing the others.
  • Link-holders — unauthenticated, read-only. The capability is possession of the unguessable URL. There is no login for readers.

Dropped from the platform spec (with reason), so the descope is explicit:

  • Multiple operators / the operator-access invariant / can_access matrix — there is one operator; ownership is implicit. The entire access-control engine collapses to "mine" + "link-published."
  • Projects, share policies (operator_only/writing_agent_only/all_*/explicit), the polymorphic shares table — no multi-principal sharing exists. A document is reachable by its unguessable URL or revoked. That is the whole access model.
  • The admin / Trust-&-Safety service (platform §12–§13): reports intake, enforcement_actions, platform_admins, the moderation queue, withhold-vs-delete, statement-of-reasons, DMCA repeat-infringer machinery — there is no tenant population to police. This is the section whose weight motivated the fork; it is gone. (The residual publisher duties that don't vanish are in §8.)
  • Legal holds / the two-counter quota / hold-invisibility / the held cache and its reconciler — all existed for the multi-tenant + preservation-duty context. Replaced by a single simple storage cap (§7) and an ordinary delete.
  • The Organization principal seam — irrelevant at one operator.

Carried over, because they are load-bearing even at this scope:

  • Sanitize-and-sandbox-on-serve (platform §6/§7). This is the one heavy piece that survives, and it survives because of the public-read requirement: anything reachable at a URL in someone's browser is published to the open web, so it must be sanitized and served in an isolated, network-restricted sandbox. The threat is not a malicious author (my agents aren't adversarial) — it is (a) an agent that gets prompt-injected into emitting something hostile, and (b) the simple fact that public bytes render in other people's browsers.
  • Per-agent API keys + revocation (rogue-agent containment).
  • Versioning (agents iterate; cheap and useful).
  • The sandbox + strict-CSP serving model (platform §7), but not the platform's per-document origins. SOLO documents are served sandboxed under a strict CSP; the isolation that matters here is document-bytes-from-the-service-origin (achieved by serving documents from a single separate content domain — intended; see §5), not documents-from-each-other. The earlier "per-document origin doubling as the capability" idea is dropped: the capability is the public_id/slug URL (§4), and the serving origin no longer carries it.

Diverged from the platform spec (the one place SOLO is not a strict subset):

  • Slug lifecycle — non-reusable, where the platform frees slugs on delete. The platform's "freed-slug" model (PLATFORM §3.2 / §3.5.1 / table row "Freed slugs") deliberately mirrors a web host: soft-deleting a document frees its slug immediately for reuse, and a restore-time collision auto-renames the restored doc. SOLO reverses this: a slug, once claimed, is retired forever (revoke/rename/clear move it to slug_tombstones, §2/§4; /s/<slug> 410s; a reclaim → 409 slug_retired). Rationale (GitHub issue #6): at SOLO scale a slug is a public, shareable, cross-linkable handle, and silent reuse — a bookmarked /s/<slug> later serving unrelated content — is a footgun that outweighs the web-host convenience the platform optimized for. This is a true behavioral divergence, not a descope: growing back toward the platform here would mean changing a rule, not adding one. (For the legitimate rename/consolidation case SOLO provides a loud, opt-in redirect — §4 — distinct from the platform's silent reuse: a retired slug can forward to another document, but only via a browser click-through or an agent's explicit follow_redirects.)

1. Principals and authentication

  • Operator — authenticates with a static operator token (OPERATOR_TOKEN, a high-entropy server secret, constant-time compared). For browser convenience there is also a signed-cookie session derived from that same token — log in once instead of pasting the token on every action — resolved after a bearer token, so programmatic callers are unchanged. The single owner; the only principal who can mint/revoke agent keys, delete or revoke documents, change a document's visibility, publish (promote) a version to the anonymous surface (§2/§4 — the second half of "only the operator makes content public," and the half that makes the phrase true of the effect rather than only of the flag), and restore a historical version. (Two classification writes that were once operator-only — tags and lifecycle status — are now reachable by an agent key too, and on both agent transports: the HTTP PUT /d/<public_id>/tags / /status routes and the MCP set_document_tags / set_document_status tools. §3 says why those two crossed the line and visibility / publication / revoke did not.) The operator is also a first-class author — it can publish and update documents directly (the JSON POST /admin/documents / PUT /admin/documents/:id door, the companion-app authoring path), not only administer what agents write. An operator-authored document records its creator as the operator principal rather than as a fake agent (see §6), so the audit trail stays honest. The operator's two-faced surface is the same authority through two skins: a JSON /admin/* API for programmatic/token-bearer use, and a server-rendered, no-JavaScript browser console at /admin/console for hands-on fleet work (the as-built console bullet below). Both resolve to the one operator principal — the console is just the cookie-session/CSRF skin over the same admin authority, not a new trust root. (Multi-operator is a deferred seam: there is exactly one operator because there is one operator token, and the cookie-session signing key is derived from it — distinct operators would require per-operator authentication and an operators table, a platform-axis evolution. The per-document/per-version authorship discriminator added for operator authoring is the only forward-compatible artifact built now; nothing here assumes the operator is plural.) There is no third-party IdP / Google-OAuth login for the operator (formally cancelled): the operator token is the sole operator trust root, and the cookie session adds no new root (rotating the token, or bumping the session epoch, ends every session). (An OAuth 2.1 + PKCE flow does exist, but it authenticates agent connectors — e.g. Claude / Cowork / ChatGPT — and resolves to an agent identity, never to operator authority. A connector's agent identity is established either when its OAuth client is minted bound to an existing agent, or — for a client minted unbound, or one that self-registered via dynamic client registration (RFC 7591; a DCR client writes no client_id ↔ agent_id row, so it is unbound by definition) — at the consent screen, where the operator picks an existing agent or mints a new one; the client_id ↔ agent_id binding is then written and props.agentId is re-derived from that binding, never trusted from the submitted form. Dynamic client registration therefore confers no authority — it only removes the manual client_id paste from the connect flow; the agent is still chosen at the operator-gated consent screen, and a dynamically-registered client expires 90 days after registration (an absolute ceiling, not reset by use). The consent screen is itself operator-gated and session-aware (the same cookie session, or a pasted token), and it lets the operator inline-approve a connector's new redirect callback — limited to a small trust-on-first-use allowlist of pre-trusted vendor hosts. That allowlist is deliberately decoupled from the consent page's CSP form-action list, which is a separate, deliberately broad set covering every legitimate OAuth callback shape (any https: host, loopback for RFC 8252 native/CLI clients, IDE custom schemes): form-action is browser defense-in-depth, not the access gate — the gate is the OAuth library's per-client registered-redirect_uri exact match plus mandatory S256 PKCE plus operator consent, so the form can only ever redirect to a target the provider already validated. Coupling the two, as an earlier build did, made the narrow vendor list double as a browser gate and silently blocked every native client whose callback no vendor list would ever contain. None of these paths confers operator authority; each resolves only to an agent identity.)
  • Operator browser console (as-built). Beyond the per-document Manage page reachable from a document shell (§4/§6), the operator has a dedicated, server-rendered admin console at /admin/console for fleet-wide work — the one place to do everything the JSON /admin/* API does without scripting a token. It is cookie-session-authed (the operator session above) and entirely no-JavaScript: every page is HTML rendered server-side, and every action is a plain GET/POST form. A logged-out visitor gets a sign-in card with no DB hit (the console is never an existence oracle), and bare GET /admin 302-redirects into it. The surface, all under /admin/console: a dashboard (/admin/console); agent + key + OAuth-client management (list/inspect agents at /admin/console/agents and /admin/console/agents/:id, mint an agent, mint a per-agent key, mint a bound OAuth client, mint an unbound OAuth client, and revoke an agent / a key / delete an OAuth client); a documents browser (/admin/console/documents?q=&tag=&slug=&cursor=&limit=) that reuses the existing hybrid-search + list cores untouched — it does no server-side visibility filtering, only renders a Public/Private badge per row, and offers the same tag/slug filters and keyword/semantic search the agent surface has; and a maintenance page (/admin/console/maintenance) fronting the operator backfill sweeps — the Vectorize re-embed and the link-graph re-extract (§3), the two derived indexes that can't be rebuilt by a SQL migration because their inputs live in R2. Per-document visibility / slug / tags / status / version-history / restore — and publication (the Publish button on each non-published version row, §4/§6) — stay on the Manage page, now understood as the per-document leaf of this same console. Two implementation notes that are deliberate, not accidental: (1) every console mutation uses the form-field CSRF ladder — a pasted operator_token field or the cookie session plus a csrf_token form field — the same ladder the /login, /logout, and Manage-page forms use, not the X-CSRF-Token header requireOperator wants (a no-JavaScript form cannot send a custom header). (2) Several console actions are POST twins of JSON DELETEs (agent / key / OAuth-client teardown) and one is a POST twin of the per-doc tag write — an HTML form can only GET/POST, so the destructive verb is carried in the path + a body field (agent_id / key_id / client_id / tags) rather than in the HTTP method. The console adds no new authority and no new core write path: it is a thin operator-UI skin over the existing *Core functions and admin handlers, so the JSON /admin/* API is unchanged by it.
  • Agent — authenticates with a per-agent API key: a ≥32-byte CSPRNG secret, stored as HMAC-SHA-256 under a server pepper, constant-time compared (a key-verification construction, not a password hash). The key resolves to an agent identity owned by the operator. Revoking a key (revoked_at) fails it closed on the next request — the rogue-agent kill switch.
  • Link-holder — not authenticated. Presents an unguessable document URL; possession is the capability (§4). Read-only, always.

There is no cross-principal access logic to evaluate. A request is operator (session), agent (key), or anonymous (public read) — and what each may do is fixed by the lists above, not computed per-document.

2. The document model

A document is an agent- or operator-authored HTML artifact, versioned, with an unguessable public_id and an optional discovery/linking slug (§3). Both the sanitized served bytes and the pre-sanitized source are stored, one of each per version (convert-and-discard has been reversed; §5); only the sanitized bytes are ever served to a browser.

The schema below is the as-built shape (Cloudflare D1 / SQLite, hence text/integer columns; ids are TEXT UUIDs and public_ids are 22-char base64url tokens):

documents
  id              text pk               -- internal row id (UUID)
  public_id       text unique not null  -- the UNGUESSABLE capability (§4). 22-char base64url CSPRNG; the shareable URL.
  slug            text                  -- OPTIONAL discovery/linking name (§3). NULL = no slug = the live slug.
                                        --   Uniqueness is a PARTIAL unique index (where slug is not null). NOT released on
                                        --   revoke/rename: the old value is RETIRED into slug_tombstones (§4), reserved forever.
  tags            text                  -- DOCUMENT-LEVEL classification, JSON-encoded array (nullable) (migration 0012).
                                        --   Like slug: identity/classification, NOT content — survives content updates and
                                        --   restore unless explicitly changed; changing tags does NOT bump a version.
  current_ver     integer               -- monotonic WRITE pointer: the newest version any principal has written; the
                                        --   write-side ETag (§6). Null only transiently at create.
  published_ver   integer               -- PUBLICATION pointer (§4, migration 0018): the version a PUBLIC document
                                        --   RENDERS to the open web. Nullable — NULL is a real, permanent state
                                        --   ("nothing has ever been published"), not an un-backfilled one. Moved ONLY
                                        --   by the operator (promote); no agent write touches it. This is the column
                                        --   that decouples "what the world sees" from "what an agent last wrote".
                                        --   Serving rule, with NO principal term:
                                        --     served = (visibility='public' and published_ver is not null)
                                        --                ? published_ver : current_ver

                                        --   is born public, coalesce(published_ver, current_ver) on the flip to public,
                                        --   nulled on revoke beside current_ver; 0018 backfilled every live public doc
                                        --   to its current_ver, so the split landed invisibly from outside.
  created_by      text references agents(id) on delete set null  -- creator AGENT; null if operator-authored OR the agent was deleted
  created_by_kind text not null default 'agent' check (created_by_kind in ('agent','operator'))
                                        --   creator's PRINCIPAL kind (§6, migration 0013). 'operator' when the operator authored
                                        --   the doc (created_by then null); disambiguates a null created_by meaning "operator"
                                        --   from one meaning "agent since deleted". DEFAULT 'agent' backfills legacy rows.
  revoked_at      text                  -- null = live. Set = the kill switch: public_id 404s; slug retired → /s/ 410s (§4).
  visibility      text not null default 'public' check (visibility in ('public','private'))
                                        --   per-document public/private axis (§4, migration 0011). ONLY gates the anonymous
                                        --   public browser surface (private → 404 to anon, like missing). Operator/agents read all.
                                        --   Operator-only to change. DEFAULT 'public' backfills legacy rows; NEW docs are born
                                        --   at DEFAULT_DOCUMENT_VISIBILITY (a [var], default 'private'), bound explicitly on write.
                                        --   Pairs with published_ver above: this decides WHETHER there is an anonymous
                                        --   surface, that decides WHAT is on it. Both are operator-only, by the same test.
  status          text not null default 'active' check (status in ('active','deprecated','archived'))
                                        --   LIFECYCLE classification (migration 0014) — the third state axis beside revoked_at
                                        --   (existence) and visibility (anonymous read): "is it current?". 'deprecated' = still
                                        --   served + searchable (marked in hits) but EXCLUDED from context-pack fills by default.
                                        --   'archived' is RESERVED in the CHECK (unsettable, no behavior in v1). Document-level
                                        --   like tags/slug: never bumps a version. Settable by an agent key OR the
                                        --   operator (§3); 'archived' by neither. NEVER gates access.
  superseded_by   text                  -- a replacement document's public_id, set only on a deprecated doc (migration 0014).
                                        --   The document-level analogue of slug_tombstones.redirect_to: surfaced LOUDLY,
                                        --   never auto-followed (packs substitute it only on explicit follow_redirects, and
                                        --   even then the original stays visibly reported). Single-hop; live-target +
                                        --   no-self-pointer validated on write; forced null when status returns to 'active'.
  created_at      text not null default (strftime now)
  updated_at      text not null         -- MODIFICATION time (migration 0017): when this document last
                                        --   changed in ANY way a corpus consumer cares about — a new version,
                                        --   a classification edit (tags/slug/visibility/status, none of which
                                        --   bump a version), or a revoke. Stamped write-path-locally by every
                                        --   mutator; never a trigger. Document-level precisely because the
                                        --   classification writes leave no versions row to date. Backfilled from
                                        --   the current version's created_at → revoked_at → created_at, so a
                                        --   pre-migration classification change under-reports until first touch.

                                        --   409 slug_redirected / follow_redirects); single-hop (points at a public_id).

public_id is globally unique; slug is optional, so its uniqueness is a partial unique index (where slug is not null) binding only live, slugged documents. A slug is not released on revoke — it is retired into slug_tombstones (above) and reserved forever, so name-uniqueness effectively spans documents.slug ∪ slug_tombstones.slug (§4). There is one operator, so no tenant partition. No deleted_at/soft-delete machinery: deletion is revoke (§4) plus, if the operator chooses, an actual purge of the bytes.

Publication — a document carries two version pointers (as-built, migration 0018). This is a concept in the model, not a storage detail: a document's versions are a chain, and two pointers walk it. current_ver is the write pointer — the newest version any principal has written, what an If-Match/ETag write races against (§6). published_ver is the publication pointer — the version the anonymous web renders — and only the operator moves it. Before the split there was one pointer, so visibility decided whether an anonymous surface existed while the content on that surface was always whatever an agent had written most recently; the operator held the door and the fleet held the contents (§4, §8 — GitHub issue #43). Now the two questions are answered by two operator-held fields: visibility = is there an anonymous surface at all, published_ver = what is on it. Three consequences for the model's vocabulary, all deliberate: "published" is no longer a synonym for "written," nor for "public" — a public document can hold newer versions that no reader has ever seen, and a private one can carry a published pointer chosen in advance (staging before the door opens is explicitly allowed); the serving rule has no principal term — a public document renders its published version to anonymous visitors, agents and the operator alike (§4), so there is never a "what the operator sees" that differs from "what a reader gets" at the same URL; and the pointer governs the HTML render path only — every credentialed surface (the text/source/links reads, all MCP reads, list, search, context packs, and the search/vector/link indexes) stays on current_ver, because those live inside the fleet, where an agent key already reads and overwrites everything, and pinning them would hide agents' work from the agents who must edit it while protecting nothing (§5). The pointer split also created a duty the model had not had before — somebody must decide, per document, that a particular revision should face outward — so the discovery surface answers it directly: the document lists and search doors filter on visibility and on publication (pending = the document holds bytes its published pointer doesn't name, current = a promote would change nothing), and visibility=public + publication=pending is the operator's review queue. That is a read filter over rows the caller already receives — both pointers have ridden every listing row since 0018 — so it moves no authority; it just means finding the work no longer requires walking the whole corpus and comparing the two numbers per row. On a private document pending also covers "never published," the resting state of a draft, and a revoked document matches neither value (revoke nulls both pointers, leaving no publication state to report).

Storage & auxiliary tables (implementation). Metadata lives in D1 (above); the two blobs per version — the sanitized render H and the retained source S (§5) — live in R2 (DOCS binding, at the per-write-attempt keys the versions row stores); the agent-OAuth provider's state lives in KV. Three tables exist beyond the core model: oauth_clients (a client_id ↔ agent_id join backing the agent connector OAuth door — §1; the row is optional — a client minted unbound lives only in KV until the operator binds it to an agent at the consent screen, so absence of a row is "unbound," and UNIQUE(agent_id) keeps it one-client-per-agent), documents_fts (an FTS5 virtual table over title/description/body, one row per live document, backing full-text search — tags are not full-text-indexed since migration 0012; the tag filter runs against documents.tags directly), and document_links (the write-time link graph, §3 — one row per distinct on-platform link in a document's current render). None of the three changes the access model; all are noted so the schema matches the build.

Search is hybrid — keyword + semantic (as-built). Beyond the FTS5 keyword index, a semantic axis exists: each live document is embedded as N ~512-token chunk vectors (Cloudflare Vectorize index, 1024-dim cosine, Workers AI @cf/qwen/qwen3-embedding-0.6b), keyed ${document_id}#${chunk}. The search surface (search_documents / the agent-reachable GET /d/search / its operator twin GET /admin/documents/search) defaults to hybrid — it runs both the keyword and the vector ranking and fuses them with Reciprocal Rank Fusion — with keyword-only and semantic-only modes available. Crucially, this changes nothing about the access model: Vectorize is a candidate ranker, never an access gate. A vector hit yields only a document id; the authoritative "is this document live / does this caller see it" check is the same D1 re-join (revoked_at IS NULL + the tag/slug filters) the keyword path uses, so a stale or not-yet-purged vector can never surface a revoked or filtered-out document. The vector store is eventually-consistent and best-effort (it is not transactional with D1; it is synced after the metadata write commits via ctx.waitUntil, and an operator backfill endpoint reconciles drift) — a missing vector degrades to "keyword still finds it," never a correctness or access fault. No new migration: the vectors live entirely in Vectorize, recoverable by id. (Vectorize sits outside the capability/visibility boundary by construction — a relevance hint layered over the authoritative D1 gate, not a new read path.)

The corpus change feed (as-built, migration 0017). Every time axis the model had until then answered "when did this appear?" — documents.created_at for the document, versions.created_at for one revision, reachable a document at a time. Nothing answered "what changed since I last looked", which is the first question an agent maintaining a knowledgebase over months asks: listing rows carried only created_at and ordered by it, so a note written in January and rewritten yesterday sorted last and read as stale. documents.updated_at (schema above) is that axis, and the listing projection carries it alongside current_version_at (the current version's write time) — the pair distinguishes "the body changed" from "only its classification did." The list surfaces gain order=created|updated and an inclusive updated_since=<ISO-8601> window, which is the whole feature: list_documents order=updated updated_since=… is the change feed, answered in the call an agent was already making. Two rules keep it honest — a cursor carries the ordering that minted it, and replaying it under the other ordering is a hard error rather than a silently skipped or repeated slice (the one failure a change feed can least afford); and a revoked document keeps surfacing in an order=updated walk, because a polling consumer learning that a document died is the point. Search takes the updated_since filter but not order (relevance ranking is its ordering — which is also why it has no cursor).

Context packs — budgeted bulk read (as-built; context-packs-design.md, migration 0014's consumer). The corpus's "bring an agent up to speed" verb: one call returns full document bodies (always the markdown derivation of the sanitized bytes — never raw HTML, never unsanitized source) filled best-first under a byte budget, with everything that didn't fit reported, never truncated (an omitted[] entry carries the reference, the reason — budget / count-cap / deprecated / unavailable / revoked — and, for deprecated members, the superseded_by pointer). Two roots, one envelope: an automatic pack amplifies a search result (include_bodies on the search surface — pure amplification, no storage), and a curated/ad-hoc pack roots at a document (load_context_pack): its members are an explicit fenced ```pack manifest block in the document's retained source when present (one slug-or-public_id per line, an [optional] tier whose entries carry one-line hints — echoed even when omitted, so the pack doubles as a menu), else the document's outbound /d/+/s/ links in order of appearance — any hand-written index page is a pack with zero ceremony, and a manifest wins when both exist. The lifecycle status axis (schema above) is the pack's trust guard: deprecated documents are excluded from automatic fills by default, so a superseded note that still ranks in search cannot confidently mis-onboard an agent. Packs change nothing about the access model: they are agent/operator-gated surfaces composing existing reads (a pack returns only documents the caller could already read_document one at a time — under the single-tenant whole-fleet trust model that is the entire corpus), and the anonymous render gate is untouched.

3. Two names, two jobs — public_id and slug

This is the crux of the design and the part most worth getting right, because it is what lets documents both be shared by link and hyperlink to each other.

  • public_id — the unguessable capability. High-entropy (≥128 bits; UUIDv4 or a ≥22-char base62 CSPRNG token). It is the security boundary (§4): the public share URL is https://<host>/d/<public_id>. Unguessable, non-enumerable, never sequential. This is what I copy and send to someone.
  • slug — the discovery + linking name. Agent-chosen, human-meaningful (north-island-report), unique. It does two jobs. (1) Discoverability — a slugged document is reachable at the short, typeable https://<host>/s/<slug> URL, which serves the document in place — the slug stays in the address bar, content-negotiated exactly like the public_id URL (§5); there is no redirect. This is for documents meant to be found by name: paste a clean link, print it on something physical, point a human at it without the opaque id. (2) Inter-document links — an agent authoring document A needs a stable, predictable name to link to document B, since it cannot use B's server-minted random public_id. So A links to B by its /s/<slug> URL, which the public /s/<slug> route serves in place at click/read time (§4). Because that URL is stable and predictable, A can link to B before B exists; the two can be authored in either order, or at once. A slug is opt-in, not a default. Unlike public_id, a slug is low-entropy and externally visible — the /s/<slug> endpoint is public (§4), so a slug is a deliberate, weaker capability traded for findability. Most documents should not carry one: a document you only ever share by its public_id URL is strictly more private without a slug, and that is the right default. Reserve slugs for documents that are meant to be found by name or linked to from another document.
  • label — optional cosmetic alias the operator might one day set when sharing, purely for human readability. It would resolve to the same document, never be the security boundary, and carry no uniqueness-collision machinery. Not built: there is no label column in the as-built schema (§2); it is a possible later addition, not a reserved column.
  • tags — document-level classification (as-built, migration 0012). A document carries an optional set of tags. Like slug, tags are identity/classification, not content: they live on documents, not versions, so they survive content updates and restore (a PUT/edit/restore that omits tags leaves them untouched, with no version bump) and only change when set explicitly. They are settable three ways: as a field on a content write (the write tools / the X-Doc-Tags header), by the operator through a no-version-bump POST /admin/documents/<public_id>/tags, and — since the agent door gained curation — by any agent key through a tag-only full replacement, which now exists on both agent transports: HTTP PUT /d/<public_id>/tags and the MCP set_document_tags tool (either way: no version bump, no re-render, no re-embed). The tool form addresses the document by public_id or document_slug and echoes back the tags that were actually stored — tags are silently sanitized to the stored charset rather than rejected (out-of-charset characters stripped, each tag truncated, duplicates dropped, the list capped), so the echo is what a caller diffs against what it sent instead of assuming the input landed verbatim. That third way is the librarian's write verb: retagging is the curation pass that has to run over the whole corpus, so making it cost a full content republish was the thing that made it unaffordable. It is not a widening of authority — an agent key already replaces any document's entire body, so re-classifying it grants strictly less. Tags drive the list_documents/search tag filter (AND semantics over documents.tags) but are not full-text-indexed (§2 — they were removed from documents_fts in 0012).
  • status — lifecycle classification (as-built, migration 0014). The third document-level classification field beside slug and tags: active | deprecated (| reserved archived), with an optional superseded_by replacement pointer. Same shape as its siblings — document-level, survives updates/restore, never bumps a version. Agent-reachable since the curation door landed, on both agent transports — HTTP PUT /d/<public_id>/status and the MCP set_document_status tool (agent key or operator; the operator twin is POST /admin/documents/<public_id>/status) — this was filed as a deferred follow-up "the trust model already permits" and is now built, on the same reasoning as tags: an author that can overwrite a document can certainly mark its own work superseded. The superseded_by replacement is named by public_id only, never by slug — it is stored as an identity rather than a name, so no later rename can silently re-point it — and it must name a different, live document (both validated on write; returning status to active forces it null). A deprecated document keeps rendering and keeps ranking in search — the field rides every listing/read row so a reader can discount it — but is excluded from context-pack fills by default (§2's pack paragraph). status never gates access anywhere; it is a trust signal, not a boundary. archived stays unsettable (reserved in the CHECK, no behavior wired).
  • Where the curation line is drawn. tags and status are on the agent door; visibility and revoke are not, deliberately. The test is not "is this write small?" but "is it the same kind of authority the caller already holds?" Re-classifying a document is a strictly-smaller power than replacing its body, which every agent key has. Visibility is the boundary between private to the fleet and readable by the anonymous internet — a different kind of authority from anything exercised inside the fleet — and revoke is irreversible (it purges bytes and retires a slug forever). Any future classification surface should be asked which side of that line it falls on before it is added. The line is drawn per field, not per transport, which is why closing the MCP gap (the two curation tools above, which the context-packs note had filed as still-deferred-over-MCP) changed no authority at all: both agent transports now carry exactly the same two curation verbs and neither carries a third. It is also why the MCP additions are not an argument by analogy for a next one — no tool takes visibility or a published version as an input, and none may be added on the grounds that these two were. (Publication — moving published_ver, §2/§4 — joined the operator-only side when it was built, on exactly this test: it is the verb that expands the anonymous surface, so it belongs beside visibility and revoke rather than beside tags and status. It is also what makes the operator-side claim true of the effect and not merely of the flag — §4, §8.)

Slug claim and addressing semantics:

  • Claiming a name is semi-permanent. A slug is set via the optional slug field/header on a write. POST /d (create) with a slug held by a live document → 409 slug_taken; with a slug that was ever claimed and has since been retired (revoked/renamed/released) → 409 slug_retired. Either way the agent picks a different name and retries. A slug, once used, is reserved forever — there is no path that returns a used name to the pool. (As-built: live slugs live on documents.slug under the partial unique index; retired slugs move to a slug_tombstones table, and a claim is checked against both sets. This reverses the original v1 "released on revoke" behavior — see issue #6.) The agent-facing rule: don't mint slugs frivolously, and to change what a name serves, update that document rather than revoking and re-publishing under the same name. One namespace is unclaimable outright (as-built, issue #4): slopcafe-docs-* is reserved for the platform's own bundled documentation, and a claim there fails with 422 invalid_slug (reason: "reserved_prefix") rather than either 409 — a different failure kind, because it is a property of the name itself rather than of the corpus: it answers the same way on an empty deployment, and it refuses the operator too. That last part is the point. The reservation exists so a seeded name means exactly one thing on every instance, which a name an operator could also hand-author would not.
  • Reads address by public_id or slug, interchangeably. GET /d/<public_id> and GET /s/<slug> serve the same document with the same content negotiation (§5), and the MCP read_document tool accepts either identifier (echoing back the resolved public_id). This read symmetry is the slug↔public_id "unification." The id-only HTTP mutation/inspection routes (PUT /d/<public_id> and its /tags / /status classification siblings; /source; /links) are bridged for slug-holders by the discovery surface: GET /d?slug=<slug> resolves a slug to its public_id (returning the 0-or-1 listing row), so a headless agent that knows only the name can still address them. (On MCP that bridge is folded into the tools themselves — the write and curation tools take either identifier; next bullet.) That listing+search surface — GET /d and GET /d/search — is reachable with an agent key OR the operator token (the HTTP twins of the MCP list_documents/search_documents tools; the operator-only /admin/documents forms are byte-identical in shape), consistent with the single-tenant whole-fleet trust model: an agent key already reads every document by id, so enumeration discloses nothing it couldn't already obtain. The operator has one further shape of that same row: GET /admin/documents/<public_id> returns a single listing row, bare — unwrapped, because nothing needs to sit beside one row (the list wraps only to carry its cursor) — the drill-down twin of the operator list, for a consumer refreshing one document's metadata after a write instead of re-fetching the whole list. It deliberately returns revoked documents, matching the list it drills into: the row degrades to nulls (no current or published version, no slug, no title or sizes) with revoked_at set, so a list→detail flow needs no special case where the list already showed the row. There is no agent-door twin, and none is needed — an agent reaches the same row through GET /d / GET /d?slug=.
  • Writes are addressed by public_id — with slug ADDRESSING as a resolver convenience, never a write-by-name verb. There is no create-or-update-by-slug route: the HTTP door is PUT /d/<public_id> and nothing else. The MCP write tools (update_document, edit_document) — and the two curation tools (set_document_tags, set_document_status) — do accept a slug in place of public_id, exactly-one-of, the same shape read_document has; but that is a resolve-then-write, not a second addressing model: the name is looked up to its live public_id first, and a name with no live document is a plain not-found, never an implicit create. The distinction matters because the corpus is addressed by slug in practice, and requiring a lookup call before every write was pure friction. A naming trap worth stating: on a content-write tool a slug plays two unrelated roles, so they are two different fields — document_slug addresses the document, slug renames it (and a rename retires the old name forever, §4). read_document can't rename, so its addressing field is just slug; the curation tools can't rename either, but they keep the document_slug spelling of the write tools they sit beside, so no field named slug ever means "address" on a tool that writes.
  • Writes never set visibility, and never publish. The slug is a settable attribute on a write; visibility and published_ver are not, on any agent door (§4). An agent write lands as a new current_ver — unless it was byte-for-byte identical to the current one, in which case it collapses to a no-op and no version is minted at all (§6) — and on a public document that new version is staged, not served, until the operator promotes it (§2, §6). Publication brought one further narrowing of the write surface: an agent may not change the slug of a public document — 403 slug_locked on PUT /d/<public_id> and on the MCP write tools; the operator's own slug change is unaffected, and an agent re-sending the document's existing slug is still a clean no-op. The reason is bandwidth, not tidiness: a slug is ~60 characters of agent-chosen text that appears verbatim in an anonymous URL, so leaving it agent-writable would have left a narrow, agent-controlled channel running straight through the publication gate. tags and status were checked against the same test and deliberately left on the agent door — neither reaches an anonymous surface.

So the mental model is: POST to create (optionally claiming a slug); PUT /d/<public_id> to revise; read by slug or public_id; classify (tags/status) in place without a version bump.

Forward links just work — no pending-link machinery. Because internal links are authored as /s/<slug> URLs resolved at click/read time by the public /s/<slug> route (which serves the target in place — §4), a link's target does not need to exist when the link is written. A link to an unclaimed slug 404s until that slug is published, then resolves; a link to a revoked slug 410s (the slug is retired, so the link never silently re-points to a different document). The platform tracks no pending_links table and does no serve-time patching or backfill — the /s/<slug> lookup is the late binding. This is exactly what lets a cross-linked set, cycles included (A↔B), be authored in any order or all at once. The details are in §4.

The link graph — backlinks as a first-class read (as-built, migration 0016, issue #40). The serving of links stays pure late binding (above), but the system now also records each document's on-platform link targets at write time: every publish/update extracts the /d/<public_id> and /s/<slug> hrefs from the sanitized render into a document_links table, in the same atomic batch as the search-index row (revoke deletes the doc's rows). Targets are stored as the raw addressed names — the table inherits the late-binding philosophy rather than fighting it — and are resolved at read time into both directions of the wiki question:

  • Backlinks ("what links here"): live documents whose current version addresses this one by public_id or live slug — a credentialed read (agent or operator, never anonymous: a backlink row describes another document, including private ones, so it belongs to the whole-fleet listing surface, which has always been credentialed). Surfaced to agents via read_document (include_links) / GET /d/<public_id>/links, and to the operator on the manage page.
  • Outbound link health: each stored target classified as live / redirected (a renamed slug's loud forward — consistent with §4's never-auto-follow rule, a redirected inbound link is deliberately not counted as a backlink) / retired / revoked / missing — the broken-link report that renames and revokes (which the slug-retirement model makes loud at serve time) now also make queryable at curation time. Orphan detection (live docs nothing links to) is the operator's whole-fleet companion view. The graph is a read model over authored content, not a new authority: it gates nothing, no surface auto-follows anything because of it, and deleting it would lose no canonical state (it is rebuildable from the stored renders via an operator backfill sweep — which is also how pre-graph documents get their rows).

4. The capability-URL security model (this is THE security boundary)

Because there is no reader login, for a public document possession of the public_id URL is authorization — there is no second check. This concentrates the entire read-security of the public surface into one mechanism, so that mechanism is treated as first-class, not a detail. (The exception is a private document — the visibility feature below: there the anonymous capability URL alone is not sufficient; the bytes serve only to the operator/fleet and the URL 404s to the open web. Possession-is-authorization remains exactly true for the public documents it was always about.) What possession buys is precise: the operator-published version, not the newest one — the URL is the capability, and published_ver (§2) decides what that capability yields.

  • High entropy, non-enumerable. public_id is ≥128 bits of CSPRNG output. No sequential ids, no /d/1, no low-entropy tokens. It cannot be brute-forced or walked. (Contrast: in the platform spec the unguessable origin was defense-in-depth behind can_access; here it is the sole boundary, so the entropy requirement is load-bearing, not belt-and-suspenders.)
  • The slug is a deliberate, weaker capability — and that asymmetry is the design, not a leak. A slugged document is reachable at the public https://<host>/s/<slug> endpoint, which serves the document in place with no auth (content-negotiated exactly like the public_id URL — §5; the slug stays in the address bar, no redirect). So slugged and unslugged documents are not equally private: a slug trades part of the public_id's ≥128-bit unguessability for a short, typeable, linkable name. A memorable slug like north-island-report is guessable, so a slugged document is discoverable by anyone who guesses or is told the name. This is acceptable precisely because the slug is opt-in and rare. The default — and the posture for the overwhelming majority of documents — is no slug: a document shared only by its public_id URL keeps the full capability boundary. Give a document a slug only when it is meant to be found by name or to serve as a link target (next bullet); for everything else the unguessable public_id alone is the stronger, correct posture. The lever against an over-shared slug is the same kill switch as any document — revoke retires the slug and 410s the /s/ lookup (§4 revoke bullet).
  • Internal links are authored as /s/<slug> URLs and resolved at click/read time by the public /s/<slug> route (served in place). An agent writes <a href="/s/section-1"> — a normal same-origin relative link the sanitizer passes through unchanged. There is no write-time link rewriting, no doc: scheme, no stored public_id substitution: the authored slug URL is exactly what gets stored and served, and the /s/<slug> endpoint (above) resolves it to the current target on every click or agent read. The cost is paid per read (a cheap serve-time lookup), not per write, and the served bytes carry the slug, not a resolved public_id. This is what makes cross-references and cycles trivial — because /s/<slug> is stable and predictable, an agent can write A linking to B and B linking to A in either order, or publish both at once, without knowing either public_id in advance. A link to a slug that isn't claimed yet simply 404s until the target is published (and 410s if the target is later revoked — the slug is retired, never re-bound to a different document); there is no forward-reference bookkeeping, no drop-and-advise pass, and no leaf-first ordering constraint. Net: agents link by memorable slug; the slug URL is public and stable; resolution is a serve-time lookup, not a write-time rewrite.
  • Per-document visibility — public vs private (as-built, migration 0011). This reverses the original "born-live" model. A document carries a visibility flag that gates only the anonymous/public browser surface: a private document returns the same opaque 404 as a missing/revoked one to an unauthenticated caller — masking discovery, never a 401, never an existence oracle — while a public one is served at its public_id/slug URLs as before — at the version the operator published, which is the second gate and the sub-bullet after next. That invariant is now enforced on every browser surface, including the two that once escaped it: the operator revoke-confirmation page (GET /d/<public_id>/revoke) resolves the operator before it reads D1, so it can no longer answer live-vs-missing to a caller holding a guessed id; and the retired-slug redirect interstitial gates its target on canRead, so a target the caller cannot read is reported as the plain 410 rather than named — refusing is deliberately indistinguishable from a dangling target, so the refusal is not itself an oracle. (Both were real leaks: renaming a private document's slug tombstones the OLD, low-entropy, probably-already-shared name with a forward pointer, which would otherwise have turned it into a title-and-address oracle for a document whose own URLs 404.) The gate does not touch authenticated principals: in the single-tenant whole-fleet trust model the operator and any active agent key already read the entire corpus, so they read every document regardless of visibility. Visibility is purely "is this exposed to the open web," not a new confidentiality boundary among insiders.
    • Born-private by default; operator-publish. New documents are born at DEFAULT_DOCUMENT_VISIBILITY — a deploy-time [var], default private — bound explicitly on each write (the column's own DEFAULT 'public' only backfills pre-0011 rows, so already-shared documents keep serving). Only the operator changes visibility — via the JSON POST /admin/documents/<public_id>/visibility, or the in-browser Manage page reached from the shell topbar's Manage… item (POST /d/<public_id>/visibility, session-cookie + CSRF; the signed-in toolbar also surfaces the current Public/Private state at a glance). No agent-facing surface sets it: no MCP tool takes visibility as an input, and the core's operator-only visibilityOverride is reachable only from the operator authoring door. Agents do, however, now see it (an earlier build hid it, on a "published is published" theory that turned out to fail agents badly): visibility rides the MCP write responses and the read envelope, and the tool text states plainly that documents are born private, that the returned URL will 404 for a logged-out human, and that the remedy is to ask the operator. The old silence produced the worst first-session outcome available — an agent handing its user a URL that 404s for them, unable to know why, with no parameter to reach for. Surfacing the state without granting the verb is the point: an agent can explain the situation and name the operator action, which is all it should be able to do. The same principle now extends to publication — publish is two operator acts, not one (open the anonymous surface, then choose what is on it), and the second is the next sub-bullet. Agents see that state too: the MCP write and read envelopes echo published_version beside visibility, so an agent that writes a new version of a public document can tell that its bytes are stored but not yet live, and report the write as pending an operator publish rather than announcing an updated page.
    • Publication — the second operator gate, and what the pair does and does not buy (as-built, migration 0018; GitHub issue #43, CLOSED). Visibility on its own gated the verb an agent doesn't have (change the flag) rather than the effect (content reaching the open web), and the gap between those was real rather than theoretical: under the single-tenant trust model (§1, §6) any active agent key may PUT to any live document — updateDocumentCore's only gate is revoked_at, with no check on the target's visibility and no created_by scoping — and every agent key can enumerate exactly which documents are public, since visibility rides every listing row. So a prompt-injected agent could read private content and republish it into an already-public document: no visibility change, no new document, no operator in the loop. The fix is not a new check on the write (writes stay unscoped — that is the trust model, deliberately) but a second pointer on the document (§2): an agent write advances current_ver, the anonymous render path serves published_ver, and only the operator moves that one. The operator promotes through POST /admin/documents/<public_id>/promote {version} — requireOperator, idempotent, no version bump, and permitted on a private document, so a corpus can be staged before the door is opened. There is deliberately no agent-reachable promote (§3's curation line: it is the verb that expands the anonymous surface). (The browser twin is built too: the per-document Manage page offers a Publish button on every version row that isn't already the published one — POST /d/<public_id>/promote behind the same operator form ladder as the page's other controls — so the act needs no scripted token.)
      • The honest as-built statement is now the strong one: an agent cannot change what an anonymous reader sees. Four limits belong with it, and they are limits of an authorization boundary, not of a containment one. (a) It inherits the operator credential — an agent that obtains the operator token is the operator, and can promote, flip visibility and revoke. (b) It is a gate, not a review: promotion moves a pointer at a whole version, so the operator approves a version number rather than a diff, and anything else that landed in that version rides along with what the operator meant to publish. The affordances to look exist (version history and restore, the source read, an operator-only banner on the shell when published_ver lags current_ver) — nothing forces the look, so the boundary's real width is one document body per operator decision. (c) A document born public publishes its own v1 at write time (the birth binding that keeps the "public ⇒ published" invariant), so a deployment that sets DEFAULT_DOCUMENT_VISIBILITY to public gets no promote in the loop for a new document's first version; the shipped private default is what keeps flag and effect aligned. (e) One further path publishes without a promote in the loop, and unlike (c) it is not governed by DEFAULT_DOCUMENT_VISIBILITY: the platform-documentation seeder (issue #4) publishes the handful of bundled docs that MCP tool descriptions instruct a model to read — born public, promoted in the same pass — so that an instruction the server issues is one its own tools can satisfy. It is bounded to be uninteresting as an attack surface: the bytes come only from the deployed build (never from a request), the slug is always in the reserved namespace no other writer may claim, and no agent door reaches it. The authorization argument is that the operator who deployed the code is the same authority a promote would ask. (d) The read side is untouched — one fleet key still reads the entire corpus and every retained source, so this closes the sink, not the source (§8). Detection still complements prevention where prevention stops: per-version authorship (migration 0013, versions.author_kind / author_agent_id) makes "an agent wrote a version of a public document" a queryable fact whether or not that version was ever promoted.
    • Slug interaction. Visibility is orthogonal to the slug. A private document keeps its slug claim (it is NOT retired — that is revoke-only); /s/<slug> simply returns 404 to anonymous and serves to the operator/agents, and making the document public again relights the same name. A private slugged document is masked, not removed.
    • The access decision is a named function — can_access. The read decision lives in one pure primitive, canRead(principal, doc) in src/access.ts: the deliberately-collapsed single-tenant descendant of the platform spec's can_access(principal, document, level) (PLATFORM §4.1) — same top-down, first-match shape, with shares / projects / soft-delete / owner-suspension all stripped away. What remains is revoked → false; operator → true; agent → true; anonymous → visibility == 'public'. Write authority and visibility-change authority are deliberately kept OUT of it (they stay separate operator checks), mirroring how the platform keeps admin authz out of can_access. This is the seam the SOLO spec previously reserved here ("a real draft/private state — born-private, explicit operator publish"): it is now built, and can_access is where future sharing/ACLs would extend rather than re-scattering the decision. One anonymous-readable surface deliberately sits outside it (as-built, issue #4): the platform's own documentation at /docs and /docs/<name>. Those bytes are not documents — they are build output compiled into the Worker from the repository, identical for every caller and already public in the open-source repo — so there is no principal to resolve, no per-instance content to gate, and no existence to be oracle about: an unknown name is a plain 404 because it names a route absent from this build, which the index itself lists. It is stated here rather than left implicit precisely because "every read goes through one primitive" is the kind of invariant that should be broken loudly or not at all. Publication is a second axis, deliberately kept out of it as well. canRead answers may this principal read this document at all; the serving rule (§2) answers which version the render path hands over, and it has no principal term. Collapsing them would have produced a per-caller view of one URL — an operator reading a public page and seeing bytes no reader can see — and it is precisely their separation that makes "what I review at this URL is what they get" true. The operator's additional reach is additive rather than divergent: the explicit, operator-gated historical-version routes (§6).
  • Revoke = the kill switch. Setting revoked_at makes the public_id return 404 immediately (subject to the same edge-cache/TTL caveat as any served-bytes change — see §5), permanently. The same batch nulls both version pointers (current_ver and published_ver, §2), so a dead document has no "published version" left to address and no stale pointer for the serving rule to honour. A revoked public_id is never reissued. Its slug is retired, not released — the /s/<slug> lookup flips to 410 Gone and the name is reserved forever; no future document can claim it (a claim attempt → 409 slug_retired). Because internal links are /s/<slug> URLs resolved at click time (above), any inbound links to a revoked document's slug 410 — they go dead, but they never silently re-point to a different document, because the name is never reissued. This closes the original v1 "late re-binding" footgun (a revoked-then-reclaimed slug serving unrelated content under the same URL): the as-built behavior was reversed per issue #6 precisely because slug reuse is surprising — a shared/bookmarked/cross-linked name should keep meaning what it meant or break loudly, never quietly swap. (The operator-controlled redirect case — repointing a retired name to a new destination via an explicit, visible redirect — is a separate, deliberate feature, distinct from silent reuse; it is built — see the slug-redirects sub-bullet immediately below.) This is the "nuke a live link" capability.
    • Slug redirects (as-built). The one legitimate "change a slug's destination" case (a branding rename, or consolidating two documents) is met not by reuse but by a loud redirect on the tombstone (slug_tombstones.redirect_to, migration 0010 — the target's public_id). Two ways one lands: (a) rename auto-forwards — when a live document's slug is changed A→B (by an agent's update_document/PUT write, OR by the operator's no-version-bump slug change on the Manage page / POST /admin/documents/<public_id>/slug), A's tombstone is created pointing at that document's own public_id, so /s/A keeps working at the new name (same-document, so it needs no separate redirect action — the operator slug change reuses the exact same retire-and-forward path as the agent write); (b) operator action — POST /admin/slugs/:slug/redirect {target_public_id} points a retired slug at a different live document (cross-document; operator-only). Resolution is loud, never silent: /s/<slug> gives a browser a click-through interstitial and an agent 409 slug_redirected, which follows only when it opts in (?follow_redirects=true, or follow_redirects:true on MCP read_document, which then stamps redirected_from). The target is stored as a public_id, so resolution is single-hop and loop-free; a revoked target dangles and falls back to 410. Two operator levers complete it: DELETE /admin/slugs/:slug/redirect drops the redirect (back to a plain 410 tombstone, still retired), and DELETE /admin/slugs/:slug is the escape hatch — force-release a tombstone entirely so the name is claimable again (the only path that un-retires a slug; for a revoke-by-mistake). Operator endpoints are requireOperator-gated (CSRF on cookie auth).
  • Referer leakage is closed. External links in served documents carry rel="noopener noreferrer" (carried from platform §6.5). The noreferrer does double duty here: besides opener-protection, it stops a document's own secret public_id URL from leaking to an external site via the Referer header when a reader clicks an outbound link. Without it, the capability secret would leak on every outbound click.

5. Sanitize and serve (carried from platform §6/§7, slimmed)

Anything reachable at a public URL is published to the open web, so the sanitize-then-sandbox pipeline is retained. It is simpler than the platform's only in that there is no adversarial-author threat model and no scripted tier — but the mechanics are the same and should be lifted from platform §6/§7 directly.

Write path (validate → sanitize → store):

  • Validate (loud, agent-facing ergonomics): check against a named blocklist (<script>, on* handlers, javascript:/data: hrefs, <iframe>/<object>/<embed>/<form>, <img>/SVG <image>, SVG <foreignObject>/<use>, <meta http-equiv=refresh>, <base>, MathML). On a hit, reject with a structured error naming the violation, so the agent can self-correct. This is feedback, not the security boundary.
  • Sanitize (the security boundary — allowlist): run an allowlist-based sanitizer (the build uses Ammonia, compiled to WASM, as a pinned profile) — only allowed tags/attributes/SVG-subset survive; everything else is dropped. The allowlist, not the blocklist, is what makes it safe (safe against unknown constructs). The sanitizer's serialized output is the bytes stored at r2_key — no re-parse and re-serialize after the last security decision, which is what manufactures mutation-XSS (the platform §6.2 ordering rule). The two forced link attributes are applied by different mechanisms, and the distinction is worth being exact about: rel="noopener noreferrer" is forced inside the sanitizer profile (ammonia's link_rel), while target="_blank" is a narrow post-pass over the sanitizer's output — a byte splice that inserts that one fixed attribute into a matching <a …> start tag and copies every other byte verbatim. No re-parse, no re-serialization, so the ordering rule holds; the splice's safety instead rests on only ever considering an <a at a text position (it skips raw-text element content — <style> has ridden through verbatim since the CSS decision below — and every other tag's interior) with every scan bounded. It fires on external http(s) links and on on-platform /d/… / /s/… links, both of which otherwise dead-end inside the render frame (see the serve path below).
  • Document-level CSS via <style> is allowed (as-built). The profile passes <style> blocks through (not just inline style="…" attributes), so a document can carry a class-based stylesheet / design system — selectors, :hover/:focus, ::before/::after, @media, @keyframes, prefers-color-scheme, @font-face with data: fonts. The sanitizer does not parse the CSS; as with inline style, the defense is the render-time CSP + iframe sandbox (the serve path below), not the sanitizer — and external CSS egress (@import url(https://…), external url(…)/@font-face src) is closed at the CSP, so such resources survive sanitize but the browser refuses to load them (a will_not_render[] advisory flags this on write). Still stripped at sanitize: <script>, external <link rel=stylesheet>, <iframe>, <meta> — the blocklist above is unchanged.
  • SVG is admitted as an explicit diagram/chart allowlist, not "SVG minus the bad parts"; <use> and <foreignObject> dropped (platform §6.3).
  • Store the sanitized bytes plus the pre-sanitized source — two R2 objects per version: the served form H at r2_key and the submitted source S at the sibling key <r2_key>.src (Markdown for a Markdown doc, the original HTML for an HTML doc), alongside the sanitizer_v stamp (so "which docs used a now-vulnerable profile" stays a WHERE clause). Convert-and-discard has been reversed (as-built): source retention is the model now, because retaining S is what lets edit_document patch the source (a Markdown doc edits its Markdown, re-renders, stays Markdown and keeps its reader theme — the bug that motivated the reversal; §6) and what unblocks lazy re-sanitization (below). The source counts toward the storage cap (§7) — single-tenant, so every stored byte is real budget. Only H ever reaches a browser; S is never served on the public render path. Source-read surfaces (the agent-scoped read_document representation:"source" MCP knob, and the credential-gated HTTP GET /d/<public_id>/source) are authenticated, never public — the HTTP route admits any non-anonymous principal: the operator OR any agent key (operator ≥ agent), never operator-only (in this whole-fleet single-tenant model any active agent key already reads and overwrites every document, so a source-read discloses no authority the caller lacks) and never agent-only (the operator is the apex principal and reads everything an agent can — gating these on the agent key alone, as an earlier build did, wrongly ranked the operator below an agent). Each source-read response carries unsanitized: true plus the stripped[] / will_not_render[] advisories, so a consuming agent is told the bytes are pre-sanitization and where the live render diverges. (Legacy/un-backfilled versions retain no source and fail loud — a structured source_unavailable, never a silent fall back to H.)
  • Resource bounds: per-document size cap, plus a two-stage depth gate — because a compromised/injected agent can still submit a pathological document, and both the parser and the converter are ~O(n²) in nesting. As built: a cheap O(n) open-tag scan runs before sanitize() and rejects a depth bomb outright (too_deep), and the precise post-sanitize DOM-depth check remains the authoritative guard, now always running on shallow, pre-screened input. The pre-scan is deliberately approximate and biased to over-count, saturating one past the limit (so a reported depth at the ceiling means "at least this deep"); the residual under-counts are constant, not per-repeated-unit, which is the only property that matters — an under-count that accumulates is a bypass, an over-count merely rejects early. (The platform's third bound — sanitize in a killable worker with a global concurrency bound, platform §6.6 — does not transfer: there is no Node event loop here, the sanitizer is synchronous WASM inside a Workers isolate, and the isolate's own CPU limit is the preemption mechanism. The depth gate is what replaces it, which is why its soundness direction is stated so precisely.)

Serve path (two readers, two representations):

  • Browser read (public, via public_id or slug): the request returns a tiny HTML shell that embeds a sandboxed <iframe>; the iframe loads the document bytes from a sibling /raw URL that carries the strict CSP — default-src 'none' (which is what denies connect-src, script-src and every other fetch directive, so there is no exfiltration channel; note the header carries no literal connect-src — the denial is inherited), frame-ancestors 'self', base-uri 'none', form-action 'none', and img-src/font-src 'self' data: plus style-src 'unsafe-inline' data: with no external origins, sandbox with no allow-scripts and no allow-same-origin (static, no script, no ambient origin) — the two flags it does grant are allow-popups allow-popups-to-escape-sandbox, purely so a real click on a target="_blank" link opens a tab: top navigation stays off, so an in-frame hop would dead-end either against the shell's frame-src 'self' (external targets) or against the shell's own frame-ancestors 'none' (on-platform targets), which is why the sanitizer injects that target on both kinds (write path above). Cache-Control: no-store. Two URLs are deliberate: frame-ancestors is header-only, so the bytes must come from an HTTP response, not srcdoc. No per-document origin. Documents are not isolated from one another (they don't need to be — my agents aren't adversarial to each other). What they do need is isolation from the service's own origin — its cookies, its session, its DOM — which matters most if a scripted tier is ever allowed. The intended hardening for that is to serve all document bytes from a single separate content domain (distinct registrable domain from the app/service origin), not a per-document origin. (Current build serves same-origin under the sandbox + strict CSP, which is the load-bearing wall; the separate content domain is the planned next layer.) A revoked public_id stops resolving and returns 404; a revoked document's (now retired) slug returns 410 Gone (§4). Publication-pinned (§2/§4): this is the one path that serves published_ver — for a public document the framed /raw bytes and the shell's own title/description/version describe the published version rather than the newest write, and the render ETag names that served version, so an operator promote changes it without a new version being written and an agent's staged write does not change it at all. A private document renders current_ver, there being no anonymous surface to protect. One consequence bites writers rather than readers: the render ETag is no longer a usable If-Match preflight, so /raw additionally returns the newest version number as x-doc-current-version — only to a non-anonymous caller, on both the 200 and the 304, because the mere existence of staged work is not public information (§6). Visibility-gated (§4): this anonymous browser read serves only public documents — a private one returns the same opaque 404 to an unauthenticated caller, and serves only to the operator (whose awh_session cookie reaches the same-origin /raw subresource — SameSite=Lax strips only cross-site requests) or to an agent key. The byte gate lives in one place, the /raw path, so nothing reaches R2 without passing it and the shell and homepage (which both embed /raw) can never leak content by forgetting. They each additionally run the same check on their own metadata, because a shell rendered before the iframe loads would otherwise disclose a private document's title, description and OG tags — so "one place" is the guarantee for bytes, not a claim that the surrounding surfaces are ungated. Because a valid public_id/slug now 404s to a logged-out operator (it can't tell its own session is missing from the doc being absent), the browser 404 is an HTML page carrying an operator "Sign in" link that round-trips back to the requested URL (/login?next=…) — so the operator signs in and lands back on the document. It is rendered identically for every browser-navigation 404 (absent, revoked, malformed, or private-to-anonymous), so it adds no existence oracle; authenticated/agent callers still receive the plain Not Found body.
  • Agent read (authenticated, via API): an agent presenting its key on GET /d/<public_id> (or GET /s/<slug>) — or the operator presenting its token, since operator ≥ agent — receives the raw sanitized HTML — the same stored bytes the iframe loads — with internal links carried verbatim as their authored /s/<slug> URLs (§4), so an agent sees the same stable links a human would click. A Markdown projection (for ingest-as-context) is a separate endpoint — GET /d/<public_id>/text (and GET /s/<slug>/text), credential-gated (operator or agent, never anonymous) — and is built, not reserved: it is derived on read from the sanitized HTML (no second stored artifact, so no drift). The representation split is by path (/ vs /text): Accept never chooses between HTML and Markdown. Accept does choose between two shapes of the same Markdown read — the default text/markdown body, or, with Accept: application/json, an envelope carrying that body plus the document's metadata (title/description/tags/slug/status/superseded_by), which the route already had in hand. Both branches send Vary: Accept. That exists to close a specific bad incentive: a caller that wanted "the text and is it current?" otherwise made two round trips or reached for /source — which hands back unsanitized bytes to ingest as context, exactly the instinct not to reward. The MCP surface mirrors all of this with one read_document tool taking a format: "html" | "markdown" knob (default markdown), which has always returned the metadata-bearing envelope. One asymmetry follows from the publication pin, and is worth knowing before it surprises someone: the credentialed HTML byte read is literally the same response a browser gets, so on a public document it returns the published version, while /text — and every other credentialed read (/source, /links, the MCP reads, list, search, packs) — returns current_ver. Same document, two versions, deliberately: the HTML bytes are the published artifact, and the machine-readable surfaces are the fleet's working copy (§2).
  • MCP Apps render (as-built) — a third render context for H, not a third serve path. Where the MCP surface is hosted inside an Apps-capable client (the io.modelcontextprotocol/ui extension), the sanitized H can also render as an inline view in the host's chat UI: the host fetches a viewer template from the service over the authenticated MCP connection and renders it — with the document's H injected as content — inside the host's own sandboxed iframe under the host's default deny-all CSP, a wall stricter than ours (no network at all). The HTML travels as a string inside the MCP tool response, never served from this service's origin, so the CSP headers of §5's serve path do not apply there and no anonymous surface is created — the read is the ordinary authenticated agent read, presentation-shaped. The load-bearing property is the same one the whole pipeline rests on: sanitized H is script-free by construction (no script, no on* handlers, no scriptable URL schemes survive the allowlist), so document content injected beside the host's tool-calling bridge cannot reach it.

Re-sanitization is now unblocked, but still deferred — not built. When the sanitizer profile hardens, new writes self-heal (they use the current sanitizer_v). Re-healing already-stored versions requires the pre-sanitized original, and the build now retains it (source S per version, above) — so the foreclosure is gone: reversing the no-original-retention decision was the prerequisite, and that reversal has landed. What remains deferred is the re-heal mechanism itself — [RESEARCH NEEDED]. The leading (operator-preferred) proposal is lazy re-heal on first read after a profile bump: on read, if a version's stored sanitizer_v is behind the current profile, re-render from the retained source, re-sanitize, re-store H, and bump the stamp — so the first reader pays the heal and everyone after gets the healed bytes, with no batch job. The open questions are where the heal fires given the streaming serve path (a re-sanitize needs buffer + WASM, which the stream can't do inline), thundering-herd idempotency on the first read after a bump, and whether a heal mints a new versions row or rewrites H in place under the same version with a new sanitizer_v. One storage constraint has since tightened, and the in-place fork must respect it: R2 version keys are now per-write-attempt (<id>/v<n>-<nonce>, §2), so a heal must overwrite at the key it read off the versions row — which is stable once that row is committed — and must never re-derive an address from (id, version_no). That is not a new obstacle (the fork always needed a stable per-version address, and the stored key is one); it is a rule about how to reach it. The sanitizer_v stamp still records which profile produced each stored blob, so "which docs used a now-vulnerable profile" remains a WHERE clause — and acting on that answer is now a buildable re-heal rather than a foreclosed one. No link interaction either way: internal links are stored verbatim as /s/<slug> URLs resolved by the public /s/<slug> route on every read (§4), so there is nothing to re-resolve — and no write-time link resolution ever existed to repeat.

6. Write semantics

  • Create: POST /d with the body (Content-Type: text/html or text/markdown; Markdown is parsed to HTML before sanitizing) and an optional slug (plus optional title/description/tags). Mints id + public_id + version 1. Fails 409 slug_taken if the slug is held by a live document. The create is one transaction: insert document (null current_ver) → insert version 1 → update the pointer (the circular-FK order from platform §3.2a). Returns the public_id (the shareable URL) and version: 1. (No model field is accepted or stored.) The operator authors through the parallel JSON door POST /admin/documents (and PUT /admin/documents/<public_id> to update) — same core write path, JSON body instead of raw bytes, and the operator may set birth visibility atomically. On the operator update door If-Match is optional (last-write-wins when omitted), the deliberate app-friendly divergence from PUT /d's required If-Match.

  • Authorship attribution (who wrote it). A write resolves to an author principal — {operator} or {agent, id} — not a bare agent id (the operator is never smuggled through as a fake agent). It is persisted in D1: documents.created_by + created_by_kind record the immutable creator, and each versions row records its own writer (author_kind + the agent id, null for the operator) — so a document's full per-version author list is queryable (e.g. an agent-created doc the operator later edits reads creator = agent, latest author = operator). The writing identity is also echoed into R2 customMetadata as before, but D1 is now the authoritative, queryable record. The current version's writer is surfaced by default, not only on request (as-built, GitHub issue #58). created_by/created_by_kind name the document's birth-time creator, which grows stale as a trust signal under the single-tenant write model — any active agent key may later overwrite a document written by another — so current_author_kind/current_author_id/current_author_name (the current version's author_kind/author_agent_id, joined for free off the same listing projection) ride every list_documents / search_documents / load_context_pack row and the MCP read_document default envelope, letting a bulk caller weight trust (operator-written vs. an unfamiliar agent id) before treating fetched content as ground truth, without a separate per-document version-history round trip. The identity recorded goes one grain finer than the agent (as-built, GitHub issue #63). An agent is a stable principal, but it is reached through a credential, and Door A's credential is an OAuth client — so two connectors authorized against the same agent used to write versions that were indistinguishable in storage (which is why allowing many clients per agent, considered in issue #37, was declined: the 1:1 binding was the only per-client provenance there was). The author principal an agent write resolves to therefore carries the client_id of the grant that authorized it, taken from the provider-validated authorization request at consent — never from the consent form, which whoever opened the link submits — and each versions row records it (author_client_id, migration 0019). It is surfaced read-only beside the rest of the authorship (current_author_client_id on listing rows and the read envelope, author_client_id on version history, and a Client column on the operator's manage page). NULL is a real state with three honest readings the sibling columns separate: an operator write, a write authenticated with a static key (no OAuth grant exists), and a version predating the record. It is attribution and nothing else — it grants nothing, gates nothing, and is not consulted by any access decision; the deliberate consequence is that a deleted client's id keeps naming the versions it wrote, because a question about the past must not be rewritten by a change in the present.

  • Update: PUT /d/<public_id> writes a new version (addressed by public_id only — there is no PUT /s/<slug>; §3). If-Match is required (omit it → 428 Precondition Required); send "v<version_no>" for optimistic concurrency (stale → 412) or * to force. The canonical strong tag is "v<version_no>", but the lenient v<version_no>/<version_no> forms are accepted too, so the integer version a read returns can be sent as-is (matching the If-None-Match tolerances on the render path). The ETag is version_no (monotonic int — "has this advanced past what I based my write on?"). A write always races current_ver, never published_ver — but note the render path's own If-None-Match ETag now names the served version (§5), so a client that preflights by HEADing /raw and reusing that ETag would send the published number on a staged public document and take a spurious 412. The newest version is returned as the x-doc-current-version response header (credentialed callers only); that is the value to preflight on, and it agrees with the ETag on a private document, so a client that prefers the header and falls back to the ETag is correct everywhere. On a public document a write is a staged write: it advances current_ver and is instantly visible to the fleet (every credentialed read, list, search and pack), while the anonymous surface keeps rendering published_ver until the operator promotes it (next bullet). An agent write that also tries to change a public document's slug is refused outright — 403 slug_locked (§3).

  • Publish (promote) — operator-only; the second half of "operator-publish" (as-built, migration 0018). POST /admin/documents/<public_id>/promote {version: n} sets published_ver = n — the version a public document renders to the anonymous web (§2, §4). It is a pointer move, not a write: no new version, no re-sanitize, no re-embed, no search/link-index resync; it stamps updated_at and nothing else, and it is idempotent (re-promoting the current choice succeeds). It is permitted on a private document deliberately — choosing what will be served before the door opens is the staging workflow, and a private document goes on rendering current_ver regardless of the pointer. Two failures are distinguished by code, not by the presence of an extra field: no live document → 404 not_found; the document is live but has no version n → 404 version_not_found, carrying that version (restore, below, answers the same pair). Telling those apart is safe here precisely because both routes sit behind the operator check — the operator can already enumerate every version at GET /admin/documents/<public_id>/versions, so the distinction discloses nothing it cannot read directly, and the agent door has surfaced this same "no such version" token on version-pinned reads all along. On an anonymous-reachable surface the identical distinction would be an existence oracle (it separates a live document from a missing one), and it is never emitted there — the opaque 404 of §4 is unchanged. requireOperator, so a token bearer or a CSRF-carrying cookie session; the per-document browser equivalent is the Manage page's Publish button (§4). There is no agent-reachable promote, and none should be added (§3's curation line).

  • Identical writes collapse (as-built). A write whose source bytes, title, description, tags and slug all match what the document already holds stores nothing: no version, no blobs, no index churn, no updated_at touch. The caller gets its ordinary success envelope with unchanged: true and version naming the version that was already there. This is a property of the write core, so it holds identically on PUT /d/<public_id>, the operator update door, the MCP update_document / edit_document tools and restore; creation is never collapsed, since a new document has no prior version to be identical to. Two consequences for the model. First, PUT is genuinely idempotent — replaying a write whose response was lost no longer forks the version chain, which If-Match alone could not give (a * retry clobbers, and a "v<n>" retry 412s on a write that had in fact succeeded). Second, a successful write no longer implies the version advanced, so "did anything change?" is a field to read rather than an arithmetic assumption. The identity test is deliberately keyed on the retained source rather than the render, and includes the sanitizer_v stamp — which promotes that stamp from a provenance record to a correctness dependency, since a byte-affecting pipeline change that lands without bumping it would suppress a re-render that ought to happen.

  • No idempotency keys. Idempotency-Key is descoped in this single-tenant build. If-Match/ETag optimistic concurrency remains the mechanism for lost-update safety (two principals writing different content); the collapse above covers the narrower duplicate-delivery case, and neither substitutes for the other. (An optional X-Content-SHA256 byte-exact integrity check on the received body exists separately, for the byte-exact curl publish path.)

  • Source currency token (source_sha256, migration 0015). Every version records the SHA-256 of its retained source S — the same bytes the X-Content-SHA256 check hashes, so for a byte-exact publish it equals the publisher's sha256sum file. It is surfaced (write response; current_source_sha256 on a body-free listing row; a representation:"source" read) so an agent holding a local copy can confirm it's still the current source — comparing hashes for pennies — and skip re-downloading the source before an edit_document (the read the edit contract otherwise prescribes). The match is exact only for a well-formed-UTF-8 file published as-is; a mismatch is a safe false negative (just re-read). This is ergonomics, not a trust boundary: it gates nothing.

  • No reader-facing write path. Only the operator (token/session) and agents (key) write.

  • Delete/revoke: operator-only. revoke flips revoked_at (the kill switch, §4), retires the slug (the name is reserved forever — /s/<slug> 410s, never reused — §4), drops the search-index and link-graph rows, and purges the R2 bytes — both H and its retained .src sibling, so the kill leaves no unsanitized source resident (§8). There is no document-level soft-delete/undelete/hold lifecycle — those were multi-tenant/preservation concerns now dropped; revoke is permanent.

    • Revoke is idempotent, deliberately. The two halves fail differently: the D1 batch (the actual kill) is atomic and lands or doesn't, while the R2 purge is a best-effort sweep over up to 2× the version count and can fail — a transient error, or a document with enough versions to exceed R2's per-call delete limit. Re-issuing the revoke is therefore the recovery path, so a second revoke on an already-revoked document succeeds and re-runs the purge rather than answering "no such document." It skips the D1 batch, so revoked_at keeps its original timestamp and the slug tombstone is not rewritten. The earlier not-found answer was actively harmful: it left unsanitized .src bytes resident forever after a single failed purge and told the operator a retry was pointless. (This is a rare case where "already done" must not report as an error, because the observable state is not what the error would claim.)

  • Version history + restore (as-built). Because versions is append-only and each version's R2 bytes are retained until revoke purges them, prior versions are readable, not just an audit trail. The operator can view any historical version in the browser (GET /d/<public_id>/v/<n> shell + /v/<n>/raw bytes, operator-gated — an operator surface orthogonal to public/private visibility) and restore one from the document-management page. Both operator actions also have JSON twins — GET /admin/documents/<public_id>/versions (the manifest) and POST /admin/documents/<public_id>/restore {version: n} — over the same cores the page uses, so a scripted operator client no longer has to scrape HTML for a first-class operator feature. The manifest marks each row on both pointers — is_current and is_published (§2) — which is what makes "the newest version and the one readers actually see are not the same" visible at a glance, and which version to hand promote. Agents read history over MCP (read_document with version to read a specific one, include_history for the newest-first manifest) — read-only; agents cannot restore in v1 (they can surface "v5 was the good one" and propose it). Restore is restore-as-a-new-version, never a pointer rewind: restoring version N re-publishes N's content (and title/description) as a new version N+1, preserving the monotonic version_no/ETag invariant (§6) — a backward current_ver move would collide with the next write. The document's current slug and tags are kept, not rolled back: both are document-level (§3), not part of a version's content. This is distinct from the (absent) document-undelete above: it recovers a prior state of a live document, not a revoked one — revoke still purges the bytes, leaving nothing to restore.

7. Storage cap

A single configurable storage cap, value chosen at build time against the selected provider's free tier(s). Enforced at write: reject a write that would exceed the cap. Accounting is a SUM over the live versions' stored bytes — both the rendered H and the retained source S (§5), since every stored byte is real budget at one operator; the platform's denormalized two-counter machinery isn't warranted at this scale. No hold-aware or operator-invisible accounting — there are no holds and one operator. Two honest properties: the check runs outside the insert batch, so two concurrent writes can both pass and overrun slightly (accepted); and the configured value fails closed — a missing, unparseable, or non-positive setting logs and falls back to the built-in default rather than silently disabling the cap, because a typo on a guardrail should not remove the guardrail.

8. The residual publisher posture (the honest, small legal note)

Descoping to single-operator removes the host-of-third-party-content duties (no DMCA safe-harbor apparatus needed — I am not hosting others' content; no report-intake/T&S surface — there is no adversarial author population). But publishing my own agent's output to public URLs is not zero-duty, and the honest residual is small and worth stating:

  • I am the publisher of record. Content at a public public_id URL is published-by-me to the open web. That is the "personal website / I publish my own output" posture — far lighter than UGC hosting, but it means ordinary content-of-the-open-web norms apply to me as publisher.
  • CSAM law is not gated on tenancy. It applies regardless of how few operators there are. At this scope there is no automated detection and no adversarial population feeding the surface — the realistic exposure is an agent being prompt-injected or malfunctioning into generating prohibited content, which I then would be publishing. The mitigation that exists is the kill switch (§4 revoke, instant) plus operator awareness. If this ever grows toward independent agents handling sensitive data or a real public population, the platform spec's §6.8/§13 preservation-and-reporting machinery is the blueprint to pull back in — do not grow the public surface without revisiting it.
  • Compromised-agent exfiltration (operator-raised): a compromised/injected agent could write secrets to a document and leak the public_id to exfiltrate via the open web. Sized as minimal — a compromised agent with outbound network access has far easier exfil paths than this tool, and I am not yet running independent agents holding sensitive context. The mitigation is built, and it is two halves rather than one (§4). The first: documents are born private by default and only the OPERATOR can flip one public, so an agent cannot mint a new anonymously-readable surface — its output stays behind the fleet credential until an operator acts, and a private doc's public_id 404s to anyone but the operator/fleet, so a leaked capability URL is not self-sufficient. (The driver there was product, not this threat — born-live is wrong for a knowledgebase — but operator-publish narrowed the threat as a hygiene side effect.) The second half closes what the first left open, immediately below.
    • The half that was missing, and now exists (GitHub issue #43 — CLOSED, migration 0018). The visibility gate on its own sat on the verb the agent doesn't have (change visibility) rather than on the effect (content reaching the open web), and the gap between them was the realistic shape of this threat rather than an exotic one. Under the single-tenant trust model any active agent key may overwrite any live document, including an already-public one — updateDocumentCore gates only on revoked_at — and every agent key can enumerate exactly which documents are public. So the exfil path that remained was: read private content (the platform's purpose is ingesting documents as agent context, read_document representation:"source" deliberately returns unsanitized bytes, and one key reads the whole corpus), then update_document / edit_document it into an existing public document. No visibility change, no new document, no operator involvement. That path is now closed on the anonymous surface, by the publication pointer (§2/§4): an agent write advances current_ver, the anonymous render path serves the operator-held published_ver, and only the operator promotes. The honest statement moved from "new content cannot be made public by an agent; existing public content can be overwritten by one" to "an agent cannot change what an anonymous reader sees" — which is the phrasing issue #43 was filed to make true.
      • What remains, stated as plainly as the gap was. The new boundary is authorization, so it inherits the operator credential — an agent that obtains the operator token is the operator. It is a gate, not a review: promotion approves a whole version rather than a diff, so its real width is one document body per operator decision and its strength is the operator's attention (the affordances to look — version history, the source read, the divergence banner on the shell — are offered, never forced). A document born public under a public default publishes its own v1 with no promote in the loop, which is what makes the shipped private default load-bearing rather than cosmetic. And the read side is untouched: this closes the sink, not the source — a compromised agent still reads the entire corpus and every retained source, and one with outbound network access still has far easier exfiltration paths than this tool, which was the original sizing and still holds. Detection continues to complement prevention: per-version authorship (migration 0013) makes "an agent wrote a version of a public document" queryable whether or not that version was ever promoted. The alternatives once listed here — gate writes landing on a public document, auto-demote to private on an agent write, per-agent created_by write scoping, scoped keys — remain not adopted, and the pointer split was chosen precisely because it leaves the single-tenant write model (§1, §6) alone.
  • Source retention (§5) leaves this analysis unmoved. The retained pre-sanitized source S is never published — only the sanitized H ever reaches a public URL, so the publisher-of-record and CSAM postures above (which are about what is published, i.e. H) are unchanged. The new raw-source channel is credential-gated — operator or agent, never anonymous — and is strictly less reachable than H (which, for a public document, already has an open-web render URL), so it adds no exfiltration path the public_id doesn't already present. The one genuinely new exposure is narrow: an agent that requests source ingests markup-form bytes the sanitizer would have stripped from the render — an XSS/markup-shape payload an HTML-naive context window might misread as instructions. That increment is covered by the unsanitized: true provenance marker + advisories on every source-read and the credential gate; it is not a new natural-language-injection surface (adversarial prose already survives into H and the Markdown projection today). Holding unsanitized bytes at rest creates no new at-rest-scanning obligation here — single-tenant, operator-owned R2 holding the operator's own agents' bytes, with no third-party UGC ingestion and no execution of stored bytes (a decided non-action, not an omission).

This section is deliberately a paragraph, not a subsystem. If any of its "if this grows" conditions start to become true, that is the signal to consult the platform spec (and, per its own §10.1, counsel) before expanding the public surface.

9. What to lift directly from the platform spec when building

To avoid re-deriving solved problems, these parts of agent-knowledge-host-spec-PLATFORM-v2.md transfer almost verbatim (with multi-tenant references stripped):

  • §6.2 validate-then-sanitize (the two-stage gate, the allowlist-is-the-boundary authority statement, the no-post-sanitize-mutation ordering rule, the stripped[] advisory).
  • §6.3/§6.3a sanitizer hardening + the pinned, versioned profile discipline (SVG allowlist, MathML/<use>/<foreignObject> handling) — though the SOLO build realizes that profile as Ammonia compiled to WASM (no DOMPurify, no jsdom shim); the sanitizer_v stamp (§2) is the pinned-version handle.
  • §6.6 resource bounds (pre-parse SAX gate, killable worker + global concurrency bound).
  • §7.2–§7.4 the iframe sandbox, CSP-as-network-boundary, and serve-time header attachment via the edge worker — but not §7.1's per-document origins. SOLO does not isolate documents from each other; the only origin isolation is document-bytes-from-the-service, via a single separate content domain (§5).
  • Nothing for slug → public_id link resolution. SOLO deliberately does not lift the platform's §3.7 doc: resolver in any form (neither serve-time nor write-time). Internal links are authored as /s/<slug> URLs and resolved by the stateless public /s/<slug> route, which serves the target in place on each read (§3–§4) — so the doc: grammar, the write-time rewrite, and the drop-and-advise machinery are not built. The /s/<slug> route is the whole resolver.
  • §11.3 write semantics (ETag = version_no, If-Match/412), minus the Idempotency-Key / new-attempt-new-key rule — idempotency keys are descoped at single-tenant scale (§6).

Everything else in the platform spec — access control, projects, sharing, admin/T&S, holds, quotas — is intentionally not carried.
